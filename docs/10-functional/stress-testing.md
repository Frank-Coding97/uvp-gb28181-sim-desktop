## 1. 目标

用一台(未来多台)机器模拟海量下级设备,量化上级平台的**承载上限、成功率、时延、稳定性**。

## 2. 媒体三档强度(FR-23)

| 档 | 内容 | 压什么 | 单机规模目标 |
|---|---|---|---|
| **A 空媒体** | 只注册/心跳/目录应答,不推流 | 平台 SIP 信令承载 | 万级 |
| **B 轻量 RTP** | 推固定/伪 PS 包,极低码率 | 平台 RTP 端口/会话/带宽调度 | 千级 |
| **C 真实码流** | 循环推真实 H.264/H.265 | 实战级带宽 + 解码承载 | 百级(受带宽限) |

`active_ratio` 控制真推流设备占比(FR-24),其余仅维持信令 —— 用少量真实流 + 大量信令,逼近真实部署形态。

## 3. 场景模型(FR-25)

TOML 定义(字段平铺在顶层,无 `scenario:` 包裹),对应 `30-crates/scenario.md` 的 `LinearScenario` 结构。示例见 `examples/scenarios/linear.toml`。关键字段:

- `base_device_id` — 起始 20 位 ID(后续 u128 递增),`password`(批量生成规则,FR-20)
- `server_host`/`server_port`/`server_domain` — 上级平台
- `ramp_per_second` — 爬坡速率(每秒拉起台数,0=一次全拉起,FR-21)
- `heartbeat_interval_secs` — 心跳间隔;`channels_per_device` — 每设备通道数
- `media_profile`(A/B/C)+ `active_ratio` + `bitrate_kbps` + `video_source` + `video_fps`(FR-23/24)
- `gb_version`(2016/2022)、`transport`(UDP/TCP)

## 4. 调度策略

### 4.1 爬坡启动(FR-21)
按 `ramp_per_second` **均匀间隔**逐台发放(1s/ramp 的绝对 deadline),而不是"攒一批后突发"
—— 批量突发既不像真实设备上线过程,也容易自己把自己打挂。例:5000 台 @ 100/s → 50s 内均匀拉起。

#### 闭环背压

爬坡原来是**开环**的:完全由时间驱动,不读任何反馈。本机一旦开始丢包(socket 缓冲不够、
fd 紧张、CPU 打满),它仍按原速继续拉设备,于是失败里混进了本机瓶颈 ——
而 `results_trustworthy` 只能**事后**告诉你"这轮不可信",一小时压测白跑。

现在每个爬坡窗口(≈ `ramp` 台)结束时看一次本地压力增量:

- 涨了 → 发放间隔翻倍(上限 `MAX_GAP_MULTIPLIER = 16`,如 200/s → 12/s),记一次
  `ramp_throttled` 并打 warn 说明"此时的失败不能算作平台承载上限";
- 没涨且此前减速过 → 间隔**折半**逐步收回(一次跳回原速容易立刻再次触发,变成振荡)。

控制的是**加压速率**而不是目标台数,所以不会偷偷少起设备,只会起得慢一些。

### 4.2 并发承载(FR-22)
- 每台设备是**轻量异步任务**(Tokio task),非独立线程。
- 心跳/重注册用**时间轮 / 分桶定时器**,万级设备不产生 sleep 惊群。
- SIP 收发共享 socket + 事务路由,避免端口耗尽。

### 4.3 推流采样(FR-24)
按 `active_ratio` 随机抽取设备子集,仅这些真推流(档 B/C),其余只维持信令。

### 4.4 主动上报施压(设备 → 平台)
除注册/心跳/推流外,可让每台设备**周期主动上报**定位(MobilePosition NOTIFY)与报警(Alarm),
模拟真实设备的上行业务对平台施压。UI 开关 + 间隔(秒),引擎侧 `Orchestrator::run(position_secs, alarm_secs)`
为每设备挂周期任务(0=关),成功数计入 `position_reported`/`alarm_reported` 指标。

## 5. 指标采集(FR-26、FR-27)

引擎每秒聚合无锁原子指标(含注册/心跳延迟直方图的 p50/p95/p99),经
**Tauri 事件 `metrics_tick`** 推 UI(见 `20-architecture/api-contract.md`),
并**每秒追加一行 JSONL 时序**;报告导出为"最终快照 + 全量时序"JSON
(见 `20-architecture/data-model.md`)。SQLite 落库仍为规划中。

指标快照带 `results_trustworthy` / `local_pressure`:出现本机队列丢弃、socket
发送失败或报文解析失败时,失败数里混进了本机瓶颈,不能直接当成平台承载上限。

| 指标 | 说明 |
|---|---|
| 注册尝试 / 成功 / 成功率 | 累计与瞬时 |
| 注册时延 | 分位数(p50/p95/p99) |
| 心跳成功率 | 周期成功比 |
| INVITE 成功率 / 建流时延 | 点播场景 |
| 活跃推流路数 | 当前真推流数 |
| 总发送码率 / 包速率 | Mbps / pps |
| 失败归因 | 超时 / 平台拒绝(再按 401·403 凭据、486·503 过载、其它三档细分)/ **本机瓶颈** / 网络其它 |
| 失败水位 | `first_failure_online`:撑到多少台在线时出现首次失败 |
| 失败样本 | 最多 20 条 device_id + 归因 + 状态码 + 当时在线数,供挑一台复现 |
| 爬坡减速次数 | `ramp_throttled`,非 0 即"本机跟不上设定速率" |

归因分档的依据是**处置动作**:401/403 是配置问题(加并发不会变好),486/503 才是承载力信号。
分类细节见 `20-architecture/data-model.md#4`。

指标热路径用原子计数 + 无锁聚合(NFR-4),不在每包路径加锁。

## 6. 压测报告(FR-28)

结束后导出 JSON,含:

- `environment` — **运行环境快照**:工具版本、OS/架构、CPU 并行度、
  **fd 软上限**、日志目录、ffmpeg 可用性。
  fd 限额尤其关键:压测按 64 台设备一个 socket 分片,fd 不够的表现是
  "注册到某个数量就大面积失败",极易被误判成平台承载不住。
  报告以前只有结果没有环境,结论既无法复现也无法采信。
- `scenario_toml_redacted` — 可复现场景。脱敏由**类型**保证:
  `LinearScenario.password` 是 `common::Secret` 且序列化时恒为占位符,
  不依赖导出代码记得替换。
- `metrics` — 最终快照(含上表全部归因字段与失败样本)。
- `series` — 每秒一行的 JSONL 时序全量(可绘曲线)。

CLI(`stress-engine`)跑完会**打印人读摘要 + 指标 JSON**,并在
`results_trustworthy == false` 时以非零码退出 —— 让 CI 里"压测跑完了"
不等于"压测结果可用"。SQLite 落库仍为规划中。

## 7. 安全边界(NFR-9)

压测流量大、破坏性强,**仅限受控内网/测试环境**;严禁对公网或未授权平台施压。UI 应在启动大规模压测前二次确认。

## 8. 验收

- 空媒体档单机 5000 台稳定注册+心跳 ≥30min,无内存泄漏(NFR-3/4)。
- 监控大盘实时显示成功率曲线与失败归因(FR-26/27)。
- 场景可保存加载复跑(FR-25)。

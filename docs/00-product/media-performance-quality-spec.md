# 视频采集性能与画质保障

本文件是待评审需求规格，不是已经承诺达成的性能指标，也不代表已批准技术方案或实现。

2026-09-14 老板明确要求开始实施开发；首批按 MPQ-03/04/08、AC-08 落实不可见预览暂停。
实施任务及逐项测试见 `docs/90-process/media-performance-implementation-plan.md`。
Windows 已选为主要构建和验证环境；其余最低设备及量化品质阈值仍保持草案状态。

## 目标

在明确的最低设备配置和工作负载内，保持用户选定的视频品质、实时性和音视频同步，
使采集、可见预览、推流、录像并行运行时，界面与电脑仍可正常交互。
优化不得通过隐藏降清晰度、降有效帧率、累积延迟或增加未授权网络负担实现。

不能对任意低配机器、任意分辨率、任意并发和任意网络同时作保证。
最终支持范围必须由发布包在真实设备上的测试确定。

## 用户故事

- 作为普通用户，我开启采集后仍能切换页面、操作其他应用，不必了解编码器参数。
- 作为联调人员，我看到的推流预览应来自实际输出码流，不能掩盖编码后的模糊、花屏或色偏。
- 作为录像使用者，我希望预览关闭、平台连接缓慢时，已启用的录像仍保持连续与完整。
- 作为低配设备用户，我希望程序自动使用已验证可用的媒体处理能力，并明确告知能力不足。
- 作为维护人员，我需要区分实际硬件工作状态、有效视频帧、资源占用和故障原因。

## 画质定义

基线是同一源素材、同一输出设置下，当前发布版本解码后的主码流。
比较对象不是摄像头原始无压缩画面的逐像素无损副本。

| 维度 | 保持要求 |
|---|---|
| 图像 | 分辨率、有效内容范围、宽高比和细节不因性能策略静默降低 |
| 时间 | 不主动降低目标帧率，不用重复旧帧伪装有效帧率，不通过持续排队掩盖吞吐不足 |
| 色彩 | 保持约定的色彩空间、范围、位深与采样格式，避免黑位、肤色、文字颜色变化 |
| 编码 | 保持用户选择的编码格式和平台兼容性，未经确认不切换 H.264/H.265 |
| 带宽 | 遵守配置的码率策略、峰值约束及存储预算，不靠无限提高码率补偿画质 |
| 音频 | 保持约定音频格式和同步，不以降低音频品质或持续漂移节省负载 |
| 可见预览 | 暂按清晰度和帧率均保持设计；能否允许降低预览规格待用户确认 |

相同分辨率和码率不等于相同画质。不同编码实现必须在相同约束下比较。
既有恒定码率与平均码率语义也需先确认，不能把正常码率波动误判为违规。
对文字、细线、滚动页面、运动人像、低照度噪声分别验收，不只看综合画质分数。

## 功能与行为要求

| ID | 要求 |
|---|---|
| MPQ-01 | 一个物理源和一组相同输出设置被多个用途使用时，不重复打开源或重复编码 |
| MPQ-02 | 不同源、不同输出设置或不同烧录叠加内容不得错误共享同一画面 |
| MPQ-03 | 用户没有查看预览时，不继续进行仅服务该预览的高开销处理 |
| MPQ-04 | 切换页面、最小化和恢复预览不得重启正在服务推流或录像的采集 |
| MPQ-05 | 只有源预览、推流、录像等需求全部消失且符合采集开关语义时，才允许释放主采集 |
| MPQ-06 | 推流预览必须保留码流验真语义；原始源画面不能冒充已编码输出 |
| MPQ-07 | 硬件可用性须包含目标设置下的实际工作结果，不能仅凭设备名称或编码器枚举判断 |
| MPQ-08 | 自动选型同时满足画质、吞吐、延迟、兼容性要求，再比较资源消耗 |
| MPQ-09 | 硬件运行失败后，只能回退到能够保持输出要求的路径；不能静默降档 |
| MPQ-10 | 回退或恢复产生的中断、丢帧、录像缺口必须如实记录，不宣称无缝 |
| MPQ-11 | 预览或某个平台慢速消费，不得无限占用内存或拖累其他正常消费者 |
| MPQ-12 | 录像写入不足时必须明确报告记录不完整，不能静默丢帧或伪造成功 |
| MPQ-13 | 性能不足时先减少无用工作与非视频界面负担；持续不足需明确提示和限制新增负载 |
| MPQ-14 | 改变输出画质、帧率、格式、带宽预算或使用外部算力必须由用户选择 |
| MPQ-15 | 诊断能显示实际处理路径、分阶段耗时、有效帧率、丢帧、积压及内存趋势 |
| MPQ-16 | 资源统计包括主程序、WebView、媒体子进程和可归因的系统媒体服务 |

## 首批验收范围草案

- 基准负载：单路摄像头或屏幕，1280×720、25 FPS、H.264、现有音频设置。
- 提升档：1920×1080、25 FPS，在通过该档能力验收的设备上承诺。
- 分别验证：仅采集、可见预览、推流、录像，以及三者同时开启。
- 多平台订阅测试用于确认资源增长边界；首版不承诺任意并发数量。
- 候选设备覆盖：无独显的办公电脑、无可用硬件编码的回退环境、独显电脑、Mac。
- 具体 CPU、内存、GPU、驱动、操作系统版本及首批优先平台待确定。
- 当前 canonical 摄像头/屏幕采集实现限于 macOS；Windows 需要纳入能力建设范围，
  不能把增加编码器选择误写为已经完成 Windows 实时采集支持。

## 验收标准草案

下列数字是待评审目标，需要先取得当前版本基线，再与目标机器能力一起定稿。

| ID | 场景与期望 |
|---|---|
| AC-01 | 同源同设置的多个用途同时开启，物理采集及视频编码实例保持单份 |
| AC-02 | 固定素材对照测试中，主码流设置不变；解码后无可见细节、文字、色彩退化；量化画质阈值在评审时锁定 |
| AC-03 | UI 常用操作响应 P95 ≤ 100 ms；稳态运行无超过 500 ms 的媒体处理所致界面冻结 |
| AC-04 | 建议本地采集回调至预览呈现延迟 P95 ≤ 250 ms，并且持续运行不增长；传感器曝光延迟另计 |
| AC-05 | 720p25 与已承诺的其他档位保持有效输出帧率，无主动降帧、持续积压或重复帧冒充达标 |
| AC-06 | 正常带宽与磁盘条件下连续运行 60 分钟，录像无软件管线导致的缺帧，音视频无持续漂移 |
| AC-07 | 建议音视频偏差绝对值 P95 ≤ 80 ms，具体采集与平台播放测量口径在技术方案中确定 |
| AC-08 | 隐藏预览后，预览专用计算与传输停止；恢复后无需重启源，已有推流与录像不中断 |
| AC-09 | 慢预览、慢平台、慢磁盘分别注入后，其他用途保持隔离，内存有界，异常准确可见 |
| AC-10 | 编码器不可用、设备忙、休眠唤醒、驱动状态变化时，不反复重启、不静默改变视频规格 |
| AC-11 | 无合格处理路径时明确提示能力不足；UI 可操作，不能显示虚假的满帧率或完整录像状态 |
| AC-12 | 画质及性能同时通过才算成功；记录 CPU、媒体引擎、内存、带宽及热稳定状态，不单凭 CPU 降低验收 |

## 非目标

- 首批只改预览需求与生命周期，不修改编码参数、主媒体协议或已评审的产品需求清单。
- 不承诺任意老旧设备运行任意规格视频；不承诺无限并发或网络、磁盘无限吞吐。
- 不默认采用外部服务器、云端处理或增加用户硬件采购。
- 不自动修改既有注册、采集开关、OSD、录像和平台协议行为。
- 不把原生源预览替换推流预览，也不以低帧率缩略图作为原画质流畅验收结果。

## 待评审问题

1. 本地可见预览是否也必须保持清晰度和帧率？当前按必须保持处理。
2. 开发验证已优先 Windows；最低配置验收设备仍待确定。
3. 最低设备与承诺视频档位、并发用途、带宽预算如何界定？建议先锁定单路 720p25。
4. 对无任何合格路径的设备，是否接受明确不支持该档位并由用户选择后续处理？
